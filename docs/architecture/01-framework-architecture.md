# Framework Architecture

## What PyForge is

PyForge is a batteries-included web framework for Python: an elegant project
structure, a capable CLI, a DI container, service providers, and conventions
instead of boilerplate — delivered as an original Python architecture on top
of FastAPI, Pydantic, and (from Phase 2) SQLAlchemy and Alembic.

## What PyForge is not

- **Not a port of another framework.** Familiar full-stack-framework ideas
  (a container, providers, named routes, an ORM with an approachable façade,
  a project generator) are worth having in Python. A literal port of another
  language's implementation (magic static-method resolution, a template
  engine, a request lifecycle built around a fixed kernel class) is not —
  Python has better tools for the same jobs: real type hints instead of
  magic method resolution, `async`/`await` instead of a synchronous-only
  kernel, dataclasses and Pydantic instead of array-based config. Every
  subsystem in PyForge is designed by asking "what does this look like as
  idiomatic, typed, async Python?", not "how do I translate another
  language's class?".
- **Not a hidden FastAPI.** FastAPI is the HTTP engine, always reachable via
  `app.fastapi`. PyForge adds structure around it; it never replaces or
  forks it. If a native FastAPI feature would work, it's expected to keep
  working unmodified inside a PyForge app (see
  [03-public-api-design.md](03-public-api-design.md#fastapi-interop)).
- **Not one big application.** The framework repository (`pyforge/`, this
  repo) never contains business logic — only reusable, generic machinery.
  Anything specific to documents, SaaS billing, multi-tenancy, etc. belongs
  in a separate application built *with* PyForge, or in an optional
  `pyforge-*` package (see [05-plugin-package-architecture.md](05-plugin-package-architecture.md)).

## Core philosophy

Simple by default, powerful when needed, convention over configuration,
production-ready, async-first, modular, testable. Concretely, that means:

- A new project (`pyforge new blog`) runs immediately with zero configuration.
- Every convenience (`User.create(...)`, `router.get(...)`, `config(...)`) is a
  thin layer over an escape hatch (a real SQLAlchemy session, a real FastAPI
  `APIRouter`, a real `os.environ`) that's always reachable for advanced
  cases. See the "four levels" table in
  [03-public-api-design.md](03-public-api-design.md#four-levels-of-usage).
- Nothing is a singleton by accident — the DI container is explicit about
  what's shared (`singleton`) versus fresh-per-resolution (`bind`).

## Layered architecture

```
┌─────────────────────────────────────────────────────────────┐
│  Your application (generated by `pyforge new`)               │
│  app/ controllers, models, services · routes/ · config/       │
└─────────────────────────────────────────────────────────────┘
                              │ depends on
┌─────────────────────────────────────────────────────────────┐
│  PyForge core  (this repo, `pyforge` package)                 │
│  ─────────────────────────────────────────────────────────── │
│  core/        Application shell (PyForge class)                │
│  container/   DI container                                    │
│  config/      Config repository + env loading + helpers        │
│  routing/     Router, RouteGroup, controller-action wiring      │
│  middleware/  Named route-guard registry                       │
│  providers/   ServiceProvider base                              │
│  console/     CLI (Typer), project generator, code generators   │
└─────────────────────────────────────────────────────────────┘
                              │ built on
┌─────────────────────────────────────────────────────────────┐
│  FastAPI · Starlette · Pydantic · (Phase 2: SQLAlchemy, Alembic)│
└─────────────────────────────────────────────────────────────┘
```

Optional subsystems (auth, queue, cache, mail, storage, notifications,
multi-tenancy) are **not** in this layer diagram on purpose — they live in
separate `pyforge-*` packages that depend on core, never the other way
around. See [02-core-package-architecture.md](02-core-package-architecture.md)
for the "core vs. package" test applied to every feature in the original
spec.

## Request lifecycle (today)

1. ASGI server (uvicorn) calls `PyForge.__call__`, which delegates straight
   to the wrapped `fastapi.FastAPI` instance — PyForge adds no request-time
   overhead of its own beyond what a plain FastAPI app already pays.
2. FastAPI's router matches the request against routes registered through
   `Router`/`RouteGroup` (mounted via `include_router`) or registered
   directly with `@app.get(...)` etc.
3. If the matched endpoint is a controller action (e.g. `UserController.show`),
   `Router` resolves a fresh `UserController` instance from the `Container`
   and calls the bound method — everything else (path/query params, request
   bodies, `Depends()`) is handled by FastAPI exactly as it would be for a
   plain function, because the wrapped endpoint keeps the original method's
   signature. See [03-public-api-design.md](03-public-api-design.md#routing).
4. Route-group middleware (named dependencies resolved from the
   `MiddlewareRegistry`) runs as ordinary FastAPI dependencies before the
   handler.
5. On process startup, PyForge's FastAPI `lifespan` calls `boot()` on every
   registered `ServiceProvider`, after all of them have already run
   `register()` — a two-phase provider lifecycle chosen because "bind
   everything, then let anything depend on anything" avoids ordering bugs
   that a single-phase `register()` would create.
